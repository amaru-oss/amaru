# Platform process resource owners

Owner: Platform (#18). These are concrete composition helpers under accepted [ADR-0068](../../../../docs/architecture/adr/0068-platform-process-readiness-and-bounded-shutdown.md), outside domain, Coordinator, ports and Worker execution logic.

`Storage` opens its own database/sql pool inside Start from a pgx stdlib connector, checks connectivity and publishes completion readiness. `Schema` runs the existing checksum-verified embedded migration runner under its existing advisory lock. Register each in its own stage of the single outer Lane, storage first. Constructors acquire no resources; create fresh owners for each process run. WaitReady may precede Start. Both initializers use the same absolute startup deadline supplied by composition; it bounds initialization, not healthy lifetime. Pass that same absolute deadline to `NewLifecycle`; its independent watchdog covers all stages, including initializers that ignore cancellation.

Storage readiness also requires PostgreSQL 16 or newer under ADR-0015/0045. After connectivity, `SHOW server_version_num` must yield an integer of at least 160000. An older version, failed query or invalid result withholds the pool and downstream readiness before migrations. The query shares the startup deadline; normal rollback closes the acquired pool. See the [Linux version-gate evidence](../../../../docs/validation/m3/2026-11-15-linux-postgres-version-gate.md).

`Lifecycle.Run` constructs one Lane with the safe diagnostic handoff and a shared positive shutdown budget; callers supply concrete stages in registration order. Its atomic `Ready()` latch opens only on aggregate readiness before the startup deadline and closes on failed runner exit and before forwarded caller cancellation or Lane teardown. The startup timer stops after readiness, so it cannot cancel healthy lifetime. Expiry remains a returned failure even when Lane regards the resulting context cancellation as intentional. Caller deadline expiry is also failure; intentional cancellation succeeds only with successful cleanup. Each Lifecycle is single-use. The production entrypoint must classify returned errors without printing them and exit unsuccessfully on failure; this helper cannot kill abandoned goroutines or owned child processes. No signal handler or restart supervisor is added alongside Lane.

The aggregate shutdown budget has subprocess coverage for a Start that ignores cancellation and a Stop that never returns. Later Stops must still be invoked with the same expired deadline; admission stays closed and Lifecycle reuse fails. The test-owned harness exits nonzero with callbacks still stranded. This is not production exit/child-reaping evidence; see the [Linux shutdown-budget record](../../../../docs/validation/m3/2026-11-15-linux-aggregate-shutdown-budget.md).

Linux `TestLifecycleSignals` sends real SIGINT and SIGTERM to healthy disposable Lifecycle processes. It checks closed admission before Start observes cancellation, joined Start before dependent Stop, reverse cleanup through Stop errors/panics and test-owned success/failure exit classification with no raw process output. Lane remains the only signal owner. This does not provide production entrypoint or owned-child reaping evidence; see the [Linux signal record](../../../../docs/validation/m3/2026-11-15-linux-lifecycle-signals.md).

Deadline failures also try to enqueue one `process.lifecycle` error record before `Run` returns, with the static cause `startup_deadline_exceeded` or `caller_deadline_exceeded` (startup expiry takes precedence). This covers deadlines that expire before Lane starts and watchdog cancellation that Lane treats as intentional. No raw returned error or custom context cause is inspected for the diagnostic. Nil, unavailable or full queues drop it without blocking; intentional cancellation adds no deadline error record. See the [Linux deadline diagnostic evidence](../../../../docs/validation/m3/2026-11-15-linux-lifecycle-deadline-diagnostics.md).

Dependents obtain the pool through `Storage.DB` after readiness. Start cancellation leaves the pool available through dependent joins. Reverse Stop joins schema/lock release and closes storage last. Storage Stop starts cleanup exactly once even when its cleanup context has already expired, waits only within that context, and returns failure if the budget is exhausted. Cleanup may continue after timeout if a driver ignores cancellation; the entrypoint must treat that as failure and exit, as ADR-0068 requires. Storage cleanup panics are contained without formatting their values. Raw driver, migration and Lane returned errors remain unsafe to print; use the existing safe lifecycle diagnostic boundary.

`Recovery` constructs the shared Coordinator from the acquired pool and runs the existing Reconcile once under the same startup deadline. Register it after Schema and messaging and before background/execution/public stages. Its completion latch withholds both readiness and `Coordinator(ctx)` on failure, panic or cancellation. Downstream owners use that same Coordinator; Stop joins reconciliation without retrying it, undoing commits or closing the pool. Coordinator options configure existing behavior; they are copied at construction and applied inside Start. This readiness gate does not add an in-process restoration path after critical failure.

`Session` obtains that recovered Coordinator, creates the in-process transport inside Start, and publishes readiness when its receive pump enters the usable link. Register it after recovery/background stages, then register `EmbeddedWorker`: its readiness completes only after the existing Worker successfully sends its initial Offer. Neither waits for a first Assignment. Unexpected nil return from either essential loop is failure; no restart is attempted. Within the cleanup budget, reverse Stop joins Worker attempts, then the Coordinator session and its receive pump, and finally closes the owned link. Start cancellation cancels attempts under existing Worker semantics and emits no synthetic Result or domain Cancel. Stop contexts bound joins; the process must exit on a timeout rather than assume abandoned work has ended. Fresh owners are required for each process run.

`HTTP` implements the ADR-0068 loopback/Auth/discovery resource owner. Register it last in the same Lifecycle, supplying an explicit private state directory, build/Instance identity, the existing operational logger and a factory for actual authorized product handlers. It binds IPv4 loopback inside Start, creates one Auth from the actual address, waits for Serve to enter Accept, and publishes discovery after handler initialization. All requests remain gated on aggregate Lifecycle readiness; health uses the existing Amaru contract and agrees with discovery metadata. No canonical directory, public configuration flag or CLI is selected here.

On stopping, aggregate admission closes before Start cancellation; upgrade request contexts are cancelled immediately. Stop closes tracked hijacked connections, permits ordinary handlers at most five seconds within the shared cleanup budget, then cancels requests and force-closes HTTP on expiry. It joins Serve and admitted handlers before closing Auth and removing discovery. Closed hijacked connections leave the registry. A cleanup timeout is failure: publication/Auth can remain owned while a handler has not joined, and the production process must exit rather than restart in place. Product Event adapters must keep subscription work within their owned handler lifetime and release it on cancellation; this owner supplies neither an Event protocol nor background subscription joins.

Linux integration tests run the real Lane, auth/discovery and existing Project settings adapter over fake storage, plus rollback, competing publication, restart, serving failure and draining/forced shutdown cases. A raw test-only upgrade demonstrates connection ownership, not the product Event protocol or browser compatibility. The settings composition test also parses shared HTTP/Lifecycle JSON, verifies trusted per-request correlation and excludes request/credential fixtures after producers join; see the [OBS-001 record](../../../../docs/validation/m3/2026-11-14-linux-obs-001-http-lifecycle-capture.md). Its diagnostic consumer is test-owned. Private discovery still fails closed outside Linux. IPv6/dual-stack product publication remains outstanding.

`operational.Logger.ConsumeLifecycle` supplies the reusable diagnostic consumer. Run it outside Lane callbacks with trusted Instance/correlation identity and a separately owned context that remains live through teardown. After diagnostic producers join, close the queue and join the consumer to drain it. Cancellation abandons queued records, including when cancellation races with queue readiness; sink failure returns a fixed safe error. A stalled writer can block the consumer, so final composition must bound its join and fail the process on expiry. Producer callbacks remain non-blocking and drop records when the bounded queue fills. [Linux consumer evidence](../../../../docs/validation/m3/2026-11-15-linux-lifecycle-diagnostic-consumer.md) covers real Lane failures and HTTP lifecycle composition; entrypoint wiring remains pending.

This is **partial implementation**, exercised with actual Lane and fake SQL connections in default tests, and PostgreSQL in the separately tagged tests. It creates no production entrypoint, configured connector, bundled PostgreSQL child owner, messaging/outbox, Provider selection, a production HTTP handler assembly, canonical state-directory selection, CLI, product Event transport, or entrypoint wiring for diagnostic consumption. It never stops an external database server, undoes migrations or deletes existing data. No new dependency or public configuration flag is introduced.

Driver panics can strand database/sql connection ownership or block a migration's deferred sql.Conn.Close before Lane sees the panic. Subprocess tests demonstrate failure without downstream admission under cancellation and a bounded shutdown budget; they do not establish graceful cleanup of a broken driver. The Lifecycle watchdog now bounds these subprocess cases without a parent timeout; production composition still needs the failure exit and child ownership described by ADR-0068. The owner expects the pinned pgx connector, not arbitrary third-party drivers.

Validation is included in root `make check` through `platform-test`. From `services/platform`, focused checks are `go test -race -count=1 ./internal/platform` and, with `AMARU_TEST_PG` pointing to a disposable server whose role can create databases, `go test -race -count=1 -tags pg ./internal/platform`. These are resource/stage tests, not full product acceptance.

Execution owner diagnostics also have [child-process channel evidence](../../../../docs/validation/m3/2026-11-14-linux-obs-001-worker-channels.md): actual Coordinator/session/Worker and Lifecycle with fake storage/Provider, terminal state and attempt identity checks, success/failure/panic/explicit cancellation, and separate stdout/stderr capture. The consumer is test-owned; production entrypoint and diagnostic consumption remain pending.

The PostgreSQL-tagged `TestPostgresExecutionShutdownAndRecovery` composes actual Storage, Schema, Recovery, Session and EmbeddedWorker owners under Lifecycle with a fake Runner. It verifies pool retention through a blocked attempt join, unchanged durable state/Events on cancellation, ordinary interruption versus idempotent requeue on fresh owner startup, stable repeated recovery and successful idempotent execution with a new fenced attempt. See the [Linux execution/PostgreSQL record](../../../../docs/validation/m3/2026-11-15-linux-execution-postgres-lifecycle.md). This is owner recreation against a live server, not process/server restart or production bootstrap.

On Linux, PostgreSQL-tagged `TestPostgresHTTPWriteDrainsBeforeStorageCloses` composes Storage, Schema, Recovery and HTTP with the existing authorized settings handler. An admitted PATCH waits while shutdown closes admission; its request then commits before HTTP/Auth/discovery join and the pool closes. Fresh owners read the durable value and reject the previous administrator credential. See the [Linux HTTP/PostgreSQL record](../../../../docs/validation/m3/2026-11-15-linux-http-postgres-lifecycle.md). Product Event transport and production handler assembly remain unimplemented by this test.

The same PostgreSQL HTTP test now covers forced drain expiry: a separate transaction locks an existing settings row, PostgreSQL reports the PATCH blocked on that lock, and the unchanged five-second HTTP drain cap cancels the real upsert. Lifecycle returns a deadline failure, joins HTTP before closing storage, and fresh owners observe the prior value with rotated credentials. The test allows eight seconds for shared cleanup so SQL cancellation and resource joins can finish after the five-second drain cap; production defaults are unchanged. See the [forced-drain record](../../../../docs/validation/m3/2026-11-15-linux-http-postgres-forced-drain.md).
